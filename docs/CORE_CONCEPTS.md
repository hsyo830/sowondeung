# 직접 이해해야 할 핵심 개념

> AI가 코드를 작성하더라도 **아래 개념은 직접 설명할 수 있어야** 합니다 (포트폴리오 면접 대비).
> 각 항목의 "확인 질문"에 답할 수 있으면 이해한 것으로 봅니다.

## 1. R3F의 렌더링 모델: React 렌더링 vs `useFrame`

- R3F는 JSX를 Three.js 씬 그래프로 바꿔 주는 React 렌더러다. **JSX는 "무엇이 존재하는가"를, `useFrame`은 "매 프레임 어떻게 움직이는가"를 담당한다.**
- `useFrame((state, delta) => { ref.current.position.y += speed * delta })` — 프레임마다 Three 객체를 직접 바꾼다. React 리렌더링은 일어나지 않는다.
- 프레임마다 `setState`를 호출하면 1초에 60번 리렌더링이 일어나 성능이 무너진다.
- **확인 질문:** 플레이어 위치는 왜 store가 아니라 ref에 두는가? 그런데 "근처 상호작용 대상"은 왜 store에 두는가?

## 2. delta time과 프레임 독립성

- 이동량 = 속도 × delta. 이렇게 해야 60Hz와 144Hz 모니터에서 같은 속도로 움직인다.
- 탭이 비활성화됐다 돌아오면 delta가 매우 커진다 → 상한(0.1초)을 두지 않으면 벽을 뚫고 지나간다.
- **확인 질문:** delta를 곱하지 않으면 어떤 기기에서 어떤 문제가 생기는가?

## 3. Canvas 좌표 변환 (CSS 크기 ≠ Canvas 크기)

- `<canvas width=512 height=768>`은 내부 픽셀 크기이고, CSS 크기는 화면 표시 크기다.
- 입력 좌표: `x = (e.clientX - rect.left) * (512 / rect.width)`
- 이 변환이 틀리면 글씨가 커서와 어긋난 위치에 그려진다.
- 변환은 순수 함수 `toLogicalPoint(clientX, clientY, rect)`로 분리한다. DOM 없이 숫자만으로 테스트할 수 있다.
- **확인 질문:** 화면이 리사이즈되면 무엇을 다시 계산해야 하는가? (답: `getBoundingClientRect`는 이벤트마다 새로 읽는다)

## 4. Pointer Events: capture와 cancel

- 마우스·터치·펜을 하나의 API로 처리한다.
- `setPointerCapture(e.pointerId)`: 포인터가 요소 밖으로 나가도 move/up 이벤트를 계속 받는다. 선이 끊기는 문제를 막는다.
- `pointercancel`: 브라우저가 제스처를 가로채거나 전화가 오는 등 입력이 중단될 때 발생한다. 진행 중인 획과 홀드를 안전하게 종료해야 한다.
- `touch-action: none`: 터치 드래그가 스크롤로 처리되지 않게 한다.
- **확인 질문:** 3초 홀드 버튼에서 `pointerleave`와 `pointercancel`을 둘 다 처리해야 하는 이유는?

## 5. UV 매핑과 CanvasTexture

- UV는 Geometry의 각 꼭짓점이 텍스처의 어느 지점(0~1)에 대응하는지를 나타낸다. `PlaneGeometry`는 좌하단 (0,0), 우상단 (1,1)이다.
- 2D Canvas는 y가 **아래로** 증가하고, 텍스처 UV의 v는 **위로** 증가한다 → `flipY = true`(CanvasTexture 기본값)가 이 차이를 맞춰 준다. 그래서 flipY를 임의로 바꾸면 글씨가 위아래로 뒤집힌다.
- 평면의 앞면(법선 +z)에서 볼 때만 좌우가 올바르다. DoubleSide를 쓰면 뒤에서 볼 때 좌우가 반전된 글씨가 보인다.
- 종횡비: Plane 1.2 × 1.8 = Canvas 512 × 768 = 2:3. 비율이 다르면 글씨가 늘어나거나 눌린다.
- 같은 Canvas에 다시 그린 뒤에는 `texture.needsUpdate = true`로 GPU에 다시 업로드해야 한다.
- **확인 질문:** 텍스처의 글씨가 위아래로 뒤집혔다면 어떤 순서로 원인을 찾겠는가?

## 6. 색공간과 톤 매핑

- CSS HEX 색상은 sRGB이고, Three.js는 내부적으로 선형 색공간에서 계산한다. 텍스처에 `colorSpace = SRGBColorSpace`를 지정하지 않으면 색이 바래 보인다.
- R3F는 기본적으로 ACES 톤 매핑을 사용해 밝기·채도가 바뀐다. 2D와 3D 색을 똑같이 맞추려면 `toneMapped={false}`를 고려한다.
- **확인 질문:** 같은 HEX인데 3D 종이가 더 어두워 보인다면 어떤 두 가지를 확인하는가?

## 7. GPU 리소스 생명주기 (dispose)

- Geometry·Material·Texture는 GPU 메모리를 차지하고, JavaScript GC가 자동으로 해제해 주지 않는다.
- JSX로 선언한 것은 R3F가 언마운트할 때 dispose한다. **직접 `new`로 만든 것(CanvasTexture 등)은 직접 dispose해야 한다.** `map` prop으로 넘긴 텍스처를 R3F가 해제해 준다고 가정하지 않는다.
- **소유권 원칙: 만든 쪽이 해제한다.** 텍스처는 `useLanternTexture`를 호출한 컴포넌트 인스턴스 하나가 소유한다. 획 데이터만 공유하고 텍스처는 공유하지 않는다.
- **공유하면 생기는 문제:** React는 커밋할 때 사라지는 컴포넌트의 effect 정리를 새 컴포넌트의 effect 실행보다 먼저 처리한다. HeldLantern → FlyingLantern 전환 때 참조 카운트가 잠깐 0이 되면서 Flying이 받기 전에 텍스처가 해제된다.
- **StrictMode와 생성 위치:** StrictMode(Next App Router 개발 모드 기본값)는 effect를 마운트 → 정리 → 재마운트 순서로 실행한다.
  - 렌더링 중(`useState` 초기화, `useMemo`)에 만들고 effect에서 해제하면, 재마운트 때 **이미 해제된 객체를 다시 쓴다.**
  - 그래서 **생성과 해제를 같은 `useLayoutEffect` 안에서 짝짓는다.** 재실행돼도 정리 단계에서 T1을 해제하고 재마운트에서 새 T2를 만들기 때문에, 해제된 객체가 다시 쓰이지 않는다.
  - `useLayoutEffect`는 페인트와 R3F 프레임 전에 실행되므로 첫 프레임부터 텍스처가 연결된다.
- **R3F의 자동 해제 범위:** R3F는 JSX 요소로 선언해서 **자기가 만든 객체**(`<planeGeometry />`, `<meshStandardMaterial />`)를 언마운트할 때 해제한다.
  - 여러 컴포넌트가 쓰는 공유 Geometry는 `geometry={SHARED}` prop으로 넘겨서 R3F의 해제 대상에서 빠지게 한다.
  - `dispose={null}`은 하위 Material까지 해제를 막으므로 쓰지 않는다.
  - Three.js는 해제된 Geometry를 다음 렌더링에서 조용히 다시 업로드하므로 화면만 봐서는 문제를 알 수 없다. `geometry.addEventListener('dispose', ...)`로 검증한다.
- **확인 질문:**
  - 천등 10개를 날린 뒤 텍스처가 해제됐는지 어떻게 확인하는가? (`renderer.info.memory.textures`)
  - Held와 Flying이 텍스처 하나를 공유하면 발사 순간 무슨 일이 생기는가?
  - `useMemo`로 만든 텍스처를 effect에서 해제하면 StrictMode에서 무슨 일이 생기는가?

## 8. 상태 머신과 순수 함수

- **순수 함수:** 같은 입력이면 항상 같은 출력을 내고, 인자나 외부 상태를 바꾸지 않는다 (부수 효과 없음).
- **결정적이지만 순수하지 않은 함수:** `drawLanternFace(ctx, color, strokes)`는 같은 입력이면 항상 같은 그림을 그리지만, 전달받은 `ctx`를 변경한다. 그래서 순수 함수가 아니라 **결정적 그리기 유틸리티**다. Vitest가 아니라 브라우저에서 눈으로 검증한다.
- 순수 함수로 분리하는 대상:
  - 좌표 변환 (`toLogicalPoint`)
  - 획 데이터 변경 (`startStroke`, `appendPoint`, `undoStroke`, `clearStrokes`, `hasInk`). 원본 배열을 수정하지 않고 새 배열을 반환한다.
  - 상태 전이, 충돌, 상호작용 판정 (`resolveInteraction`)
- 천등 상태(NONE/BLANK/WRITTEN/LIT)와 허용 전이 표를 순수 함수로 표현한다 → UI 없이 테스트할 수 있다.
- **상호작용 실행 시점 재검증:** 버튼이 보인다고 해서 실행해도 된다는 보장은 없다. 클릭하는 순간에는 이미 플레이어가 범위 밖에 있을 수 있다. 표시와 실행이 같은 순수 함수를 각각의 시점에 다시 호출해야 둘 사이에 불일치가 생기지 않는다.
- 액션이 현재 상태를 검사하기 때문에 **중복 발사 방지가 액션 자체에서 보장된다** (멱등성). 버튼 비활성화는 보조 수단일 뿐이다.
- 천등 상태(무엇을 들고 있나)와 모드(무엇을 보고 있나)를 분리한다. 하나로 합치면 경우의 수가 곱해진다.
- **확인 질문:** 3초가 지난 순간 클릭 핸들러와 E키 핸들러가 동시에 발사를 호출하면 어떻게 되는가? `undoStroke`가 원본 배열을 직접 `pop()`하면 '작성 취소' 시나리오에서 무엇이 깨지는가?

## 9. Zustand 구독과 리렌더링

- `useGameStore(s => s.mode)`처럼 셀렉터로 필요한 값만 구독하면, 그 값이 바뀔 때만 리렌더링된다.
- `useFrame` 안에서는 훅 대신 `useGameStore.getState()`로 읽는다. 구독하지 않으므로 리렌더링이 없다.
- **확인 질문:** HUD 전체가 프레임마다 리렌더링된다면 무엇을 의심하는가?

## 10. XZ 평면 충돌 (원 · AABB)

- 플레이어(원)와 사각형의 겹침: 원 중심에서 사각형 위 가장 가까운 점까지의 거리가 반지름보다 작으면 충돌이다.
- 원과 원의 겹침: 두 중심 사이 거리가 반지름의 합보다 작으면 충돌이다. 나무줄기·바위는 원, 테이블은 사각형으로 근사한다.
- 축별 해석: X로 이동한 뒤 충돌하면 X 이동을 취소하고, Z도 같은 방식으로 처리한다 → 장애물을 따라 미끄러진다.
  - 한계: 한 축 키만 누른 채 원이나 사각형 모서리에 정면으로 부딪히면, 막힌 축을 취소하고 나면 남는 이동이 없어서 멈춘다. 접촉면의 법선 방향으로 밀어내는 방식은 이런 경우에도 곡면을 따라 돈다.
- 부동소수점: `1.6 - 2`는 정확히 `-0.4`가 아니다. 경계에 '정확히 닿는' 값으로 테스트하면 결과가 오차에 따라 바뀐다. 테스트는 경계에서 조금 떨어진 값으로 쓴다.
- **확인 질문:** 두 장애물 사이 통로 폭이 플레이어 지름보다 좁으면 어떻게 되는가? W만 누른 채 둥근 바위 옆면에 부딪히면 왜 멈추는가?

## 10-1. 바닥 높이 격자 (heightfield)와 이동 가능 판정

- 지형 메시 위를 걸으려면 "이 (x, z)에서 바닥 높이가 얼마인가"를 알아야 한다. 매 프레임 메시에 광선을 쏘는 대신, 로드할 때 일정 간격(0.5)으로 광선을 쏴서 **높이 격자**를 만들어 둔다.
- 격자 사이 높이는 주변 4점을 **쌍선형 보간**한다. 4점 중 하나라도 바닥이 없으면(광선이 아무것도 맞히지 못함) 그 칸은 허공이다.
- 이렇게 하면 이동 판정(`canStandOnTerrain`, `canStep`, `resolveMove`)이 Three 없이 숫자만으로 동작해서 Vitest로 테스트할 수 있다. 광선을 쏘는 쪽(컴포넌트)과 판정하는 쪽(순수 함수)을 나눈 것이다.
- 단차·경사: 이동 전후 높이 차가 너무 크거나(단차), 거리에 비해 크면(경사) 막는다. 물리 엔진 없이 "올라갈 수 없는 곳"을 표현하는 가장 단순한 방법이다.
- 나무·바위는 격자에 넣지 않는다. 바닥 메시만 샘플링하므로, 장애물 위로 "올라가는" 일이 원천적으로 없다. 장애물은 2D 충돌(§10)이 막는다.
- **확인 질문:** 광선을 모든 메시에 쏴서 높이를 재면 어떤 문제가 생기는가? 격자 간격을 2로 늘리면 무엇이 달라지는가?

## 11. Next.js에서 WebGL을 다루는 방식

- Server Component에서는 `window`나 WebGL을 쓸 수 없다. 3D 영역은 `'use client'` 컴포넌트 안에서 `dynamic(() => import(...), { ssr: false })`로 불러온다.
- `ssr: false`는 Server Component에서 사용할 수 없다 (Next 16 문서).

## 12. 패키지 버전과 peer dependency

- peer dependency는 "이 라이브러리는 호스트가 설치한 이 범위의 버전과 함께 동작한다"는 선언이다. R3F 9.8.2는 `react >=19 <19.4`를 요구한다.
- `package.json`의 `^19.3.0`은 19.x 범위 안에서 최신으로 올라갈 수 있다는 뜻이다. 그러면 19.4가 설치되어 R3F 범위를 벗어날 수 있다. 그래서 캐럿 없이 정확한 버전(`19.3.0`)으로 고정하고 `--save-exact`로 설치한다.
- `--force`나 `--legacy-peer-deps`는 경고를 숨길 뿐 호환성 문제를 해결하지 않는다.
- **확인 질문:** `npm ls react`에 `invalid`가 표시되면 무엇을 의미하는가?

## 13. 스켈레탈 애니메이션 (GLB + AnimationMixer)

- 리깅된 모델은 메시와 스켈레톤(본 계층)으로 이루어지고, 애니메이션 클립은 본의 회전·위치를 시간에 따라 바꾼다.
- `AnimationMixer`가 클립을 재생한다. 매 프레임 `mixer.update(delta)`를 호출하고, `action.crossFadeTo()`로 Idle과 Walk를 부드럽게 섞는다.
- 클립 전환은 상태가 **바뀔 때만** 한다. 매 프레임 `play()`를 호출하면 애니메이션이 처음으로 계속 되돌아간다.
- 이동·충돌(어디에 있나)과 모델·애니메이션(어떻게 보이나)을 분리한다. 그래야 모델을 바꿔도 게임 로직은 그대로 유지된다.
- **루트 모션 vs In Place:**
  - 루트 모션 클립은 엉덩이 본이 실제로 앞으로 이동한다.
  - In Place 클립은 제자리에서 걷는 동작만 한다.
  - 이 프로젝트는 위치를 코드(`PlayerController`)가 정하므로 In Place를 쓴다. 루트 모션을 쓰면 코드 이동과 겹쳐서, 모델이 충돌 위치보다 앞서 나가거나 루프할 때마다 뒤로 튄다.
- 본에 물건을 붙일 때는 본의 자식으로 넣으면 본의 스케일과 흔들림까지 그대로 물려받는다. 그래서 월드 위치만 복사하는 방식을 쓴다.
- **리깅 ≠ 애니메이션:** 스켈레톤이 있다고 클립이 들어 있는 것은 아니다. `gltf.animations`가 빈 배열이면 재생할 동작이 없고, 모델은 바인드 포즈(T 포즈)로 서 있다. 이 프로젝트의 처음 제공된 `character.glb`가 그 상태였다 (Mixamo 클립을 통합해 해결).
- **클립은 본 이름으로 연결된다:** 클립의 트랙 이름은 `본이름.quaternion` 형태다. 다른 스켈레톤(예: `mixamorigHips`)용 클립을 `Hips_01` 스켈레톤에 재생하면 아무 본도 움직이지 않는다. 그래서 같은 캐릭터로 만든 클립이 필요하다.
- **트랙이 움직이는 노드를 확인한다:** Mixamo FBX의 위치 트랙은 `Hips`가 아니라 루트 그룹(`BaseMesh_Chibi`)을 움직였다. 단위 변환 스케일(0.01)을 그 노드에 걸면 위치 값까지 0.01배로 해석이 바뀌므로, 스케일은 그 위의 새 부모에 둔다.
- **In Place 검증:** 루트 위치 트랙의 처음 값과 마지막 값이 같으면 제자리 클립이다. 루트 모션 클립은 한 루프에 앞으로 크게 이동한다 (이번 첫 Walking: z 23 이동).
- `AnimationMixer`도 `new`로 만드는 객체다. effect에서 만들고, 정리 함수에서 `stopAllAction()`·`uncacheRoot()`로 정리한다.
- **확인 질문:** 캐릭터가 멈춰 있는데 Walk 애니메이션이 계속 재생된다면 어디를 확인하는가? 걷는 동안 캐릭터가 1초마다 뒤로 튄다면 원인은 무엇인가? Mixamo에서 받은 클립을 재생했는데 캐릭터가 꼼짝하지 않는다면?

## 14. 외부 GLB 에셋 다루기 (배경·캐릭터)

- **구조를 먼저 확인한다:** GLB는 앞부분이 JSON(노드·메시·재질·애니메이션 목록), 뒷부분이 바이너리(정점 데이터)다. JSON만 읽어도 노드 이름, 계층, 변환 행렬, 접근자의 min/max(로컬 바운딩 박스), `asset.extras`(제작자·라이선스)를 알 수 있다.
- **월드 좌표는 계층을 곱해서 구한다:** 노드의 실제 위치 = 부모 행렬들 × 자기 행렬. Sketchfab에서 내보낸 GLB는 루트에 Z-up → Y-up 회전이 걸려 있고, FBX에서 온 모델은 0.01 스케일이 걸려 있기도 하다. 바운딩 박스는 꼭 월드 행렬을 적용한 뒤에 본다.
- **이름은 믿되 확인한다:** 내보낸 이름이 `Cube.001`, `Icosphere.023`처럼 의미 없는 경우가 많다. 재질 이름(`Fire`, `LightWood`)과 위치·크기를 함께 보고, 렌더링해서 눈으로 확인한 뒤에 "이것이 테이블이다"라고 정한다. GLTFLoader는 이름의 `.`을 지운다 (`Cube.001` → `Cube001`).
- **충돌 범위는 바운딩 박스가 아니라 단면으로:** 비스듬한 나무, 뿌리가 퍼진 테이블은 바운딩 박스가 실제 부딪히는 부분보다 훨씬 크다. 몸통 높이에서 메시를 수평으로 잘라 얻은 단면이 실제 충돌 범위다.
- **`useLoader` 결과는 캐시되고 공유된다:** 같은 URL이면 같은 객체를 돌려준다. R3F는 `<primitive object>`로 넣은 객체를 언마운트할 때 해제하지 않는다. 그래서 GLB 씬·재질을 직접 dispose하지 않고, prop으로 바꾸지도 않는다 (스케일은 감싸는 group에 준다).
  - 재질 객체를 다른 메시에 `material={...}` prop으로 넘겨도 R3F는 그 재질을 해제하지 않는다 (해제 대상은 JSX로 선언해 R3F가 만든 객체뿐).
- **경계 숨김:** 섬처럼 끝이 있는 에셋은 같은 재질의 연장 평면 + 안개로 끝을 숨길 수 있다. 안개 색과 배경색을 같게 두면 먼 곳이 하늘과 이어진다.
- **라이선스:** `asset.extras.license`를 확인한다. CC BY는 출처 표기, CC BY-NC는 비상업 용도만, SA는 수정한 에셋을 같은 라이선스로 배포해야 한다는 뜻이다.
- **확인 질문:** 노드 이름만 보고 `Cube.001`을 테이블로 확정하면 어떤 위험이 있는가? 같은 GLB를 두 군데에서 `<primitive>`로 쓰면 무슨 일이 생기는가? 배경을 π 회전했을 때 GLB에서 측정한 좌표는 어떻게 바뀌는가?

## 15. 바라보는 방향 판정 (내적)과 히스테리시스 — 3단계

- **거리만으로는 부족하다:** 탁자 옆을 지나가기만 해도 버튼이 뜨면 안 된다. 그래서 "가까운가" + "그쪽을 보고 있는가"를 같이 본다.
- 바라보는 방향 벡터는 yaw에서 나온다: `(sin yaw, cos yaw)` (yaw 0 = +z, `getYawFromDirection`과 같은 규칙).
- 대상 방향 = 플레이어 → **대상 표면에서 가장 가까운 점**. 긴 탁자도 어느 변 앞에 서든 그 변을 정면으로 본다.
- 두 단위 벡터의 내적 = 사이각의 cos. `cos ≥ 0.5`면 60° 안이다. `acos` 없이 비교만 하면 된다.
- **카메라가 비추는 것 ≠ 캐릭터가 바라보는 것:** 카메라는 고정 오프셋이라 늘 같은 쪽을 본다. 판정은 캐릭터의 입력 방향(`targetYaw`)으로 한다. 모델이 보간 중인 회전이 아니라 입력이 정한 목표 방향이라, 키를 누른 순간 판정이 바뀐다.
- **히스테리시스:** 들어오는 기준(거리 0.7, 60°)보다 나가는 기준(0.9, 75°)을 넓게 둔다. 경계에 서 있을 때 버튼이 깜빡이거나, 누르려는 순간 조금 돌아서 사라지는 것을 막는다. 이전 상태(`currentId`)를 인자로 받으므로 함수는 여전히 순수하다.
- **확인 질문:** 히스테리시스 없이 경계에 서 있으면 어떤 일이 생기는가? 표시는 히스테리시스를 쓰는데 실행은 안 쓰면 어떤 불일치가 생기는가?

## 16. 3D 위치에 HTML 붙이기 (투영)와 inverted hull 테두리 — 3단계

- **월드 → 화면:** `vector.project(camera)`는 NDC(-1~1)를 돌려준다. 화면 픽셀 = `((x+1)/2 × width, (1-y)/2 × height)`. NDC는 위가 +, CSS는 아래가 +라서 y를 뒤집는다. `z > 1`이면 카메라 뒤쪽이다.
- 버튼·작성 Canvas 위치는 매 프레임 바뀌므로 React state가 아니라 **DOM 요소의 style을 useFrame에서 직접** 쓴다 (값이 바뀔 때만). React는 `style` prop을 넘기지 않은 요소의 인라인 스타일을 건드리지 않는다.
- **원근:** 비스듬히 내려다본 사각형은 화면에서 가까운 변이 넓은 사다리꼴이 된다. 직사각형 2D Canvas를 그대로 맞출 수 없으므로 가장 넓은 너비에 맞춰 3D 종이를 덮고, 카메라가 거의 내려온 뒤에 Canvas를 나타나게 한다.
- **inverted hull 외곽선:** 같은 Geometry를 `BackSide` 단색 재질로 조금 키워 한 번 더 그린다. 원래 메시가 앞을 가려서 실루엣 둘레만 테두리로 남는다. 후처리 패스·셰이더·추가 패키지가 필요 없고, 원하는 메시에만 붙일 수 있다.
  - 한계: 중심 기준으로 키우므로 오목한 부분은 두께가 일정하지 않다. 법선 방향으로 밀어내려면 셰이더가 필요하다 (범위 밖).
  - 축마다 배율을 따로 정해야 납작한 상판도 같은 두께로 보인다: `1 + 2t / (크기 × 월드 스케일)`.
- **확인 질문:** 버튼 위치를 useState로 관리하면 무엇이 문제인가? hull을 `FrontSide`로 그리면 어떻게 보이는가?

## 17. 본 위치 따라가기 (부착 없이) — 3단계

- 천등을 손 본의 자식으로 넣지 않고, 캐릭터의 **스케일 없는 바깥 그룹**의 자식으로 둔 뒤 매 프레임 손 본의 월드 위치를 그 그룹의 로컬 좌표로 바꿔(`worldToLocal`) 위치만 복사한다.
  - 회전은 바깥 그룹(캐릭터 Y 회전)만 따른다 → 손목 회전으로 천등이 뒤집히지 않는다.
  - 스케일(4 × 0.01)을 물려받지 않는다.
  - 캐릭터와 함께 숨겨진다 (작성 모드).
- `matrixWorld`는 렌더할 때 갱신된다. useFrame에서 읽기 전에 `bone.updateWorldMatrix(true, false)`로 조상까지 갱신한다. 손과 바깥 그룹이 같은 시점 값이 되어 useFrame 실행 순서와 상관없이 상대 위치가 맞는다.
- **확인 질문:** 손 본에 바로 `add()`하면 크기·회전이 어떻게 되는가? `updateWorldMatrix` 없이 `matrixWorld`를 읽으면 어떤 지연이 생기는가?

## 18. 홀드 입력: 경과 시간으로 재기 — 4단계

- **진행률 = (지금 − 누르기 시작한 시각) / 3000ms.** `performance.now()`로 잰다. `setTimeout`이나 프레임마다 `+= delta`로 쌓으면 탭 전환·프레임 드롭 때 시간이 어긋나고, 취소·재시작 처리가 복잡해진다. 시작 시각 하나만 기억하면 언제 읽어도 정확하다.
- **상태 = `IDLE` 또는 `HOLDING(시작한 장치, 시작 시각)`** (`lib/game/launchHold.ts`, 순수 함수). 이 모양이 우회를 막는다.
  - 누르는 중에 들어온 시작(F 반복 keydown, 다른 장치의 pointerdown)은 **무시**한다 → 시작 시각이 바뀌지 않는다.
  - **시작한 장치**를 떼면 IDLE → 0%. 진행률을 '쌓는' 변수가 없으므로 짧게 여러 번 눌러 3초를 채울 수 없다.
  - 다른 장치를 떼는 것은 무시한다 (키로 누르는 중에 클릭했다 떼도 취소되지 않음).
- **keydown 자동 반복:** 키를 누르고 있으면 OS가 keydown을 계속 보낸다 (`event.repeat === true`). 상호작용 액션에서는 이것을 무시한다. 무시하지 않으면 '누를 때마다 다시 시작'이 매 반복마다 일어난다.
- **취소 경로를 모두 막는다:** keyup·pointerup·pointerleave·pointercancel만으로는 부족하다. 창이 포커스를 잃으면 keyup이 오지 않는다 → `window blur`·`visibilitychange`에서도 취소한다. 모드가 바뀌거나(작성 모드) 상태가 LIT이 아니게 되면 store 구독으로 즉시 취소한다.
- **매 프레임 React 상태를 바꾸지 않는다:** 누르는 동안만 `requestAnimationFrame`으로 진행 바의 `style.transform = scaleX(p)`와 퍼센트 `textContent`를 DOM에 직접 쓴다. `width` 대신 `scaleX`를 바꾸면 레이아웃 계산 없이 합성만 다시 한다.
- **정확히 한 번 발사:** 완료 시 ref(지역 변수) 가드를 **먼저** 켜고 `launchLantern`을 부른다. store 액션도 LIT일 때만 성공하므로 같은 프레임에 두 경로(키·포인터)가 동시에 완료돼도 두 번째는 거부된다 (이중 방어).
- **확인 질문:** 0.9초씩 네 번 누르면 왜 발사되지 않는가? F를 누른 채 다른 창을 클릭하면 어떤 이벤트가 오고 어떤 이벤트가 오지 않는가? 진행률을 `useState`로 관리하면 무엇이 문제인가?

## 19. 발사 인스턴스와 리소스 수명 — 4단계

- **데이터와 표시를 나눈다:** store의 `flying`에는 발사 순간의 **직렬화할 수 있는 값**(id·색·획 참조·출발 위치·방향·drift)만 있다. 매 프레임 바뀌는 위치·회전·발광은 각 `FlyingLantern`이 ref와 Three 객체에 직접 쓴다. 그래서 천등이 날아가는 동안 store는 바뀌지 않고, 목록이 바뀔 때(발사·제거)만 React가 다시 렌더한다.
- **한 번의 갱신으로 넘긴다:** `launchLantern`은 `held = NONE`과 `flying에 추가`를 `set` 한 번으로 한다. 같은 커밋에서 HeldLantern의 모델은 언마운트되며 **자기** 텍스처를 해제하고, FlyingLantern은 마운트되며 같은 획으로 **새** 텍스처를 만든다 (§7 소유권). 두 텍스처가 독립이라 순서와 상관없다.
- **key = 천등 id:** 새 천등을 받아 손 천등이 다시 마운트돼도 발사 천등의 key는 바뀌지 않으므로 기존 인스턴스(와 애니메이션 진행)는 그대로다. 다음 천등은 새 id·빈 획으로 시작해서 이전 데이터가 섞이지 않는다.
- **수명 끝 = 정확히 한 번:** 제거 조건(높이 40 / 20초)은 순수 함수가 판정하고, 조건을 처음 만족한 프레임에 ref 가드를 켠 뒤 `removeFlyingLantern(id)`를 한 번 부른다. 액션도 '없는 id면 변화 없음'이라 두 번 불려도 안전하다. 목록에서 빠지면 언마운트 → 텍스처 해제. 공유 Geometry는 prop으로 넘겼으므로 해제되지 않는다.
- **개수 제한:** 최대 5개, 넘으면 배열 앞(가장 오래된 것)부터 버린다. 버려진 인스턴스도 같은 언마운트 경로로 텍스처를 해제한다.
- **비싼 자원은 개수를 고정한다:** 발사 천등에는 pointLight를 붙이지 않는다 (라이트 수가 바뀌면 모든 재질 셰이더 재컴파일 + 라이트당 조명 계산). 손 천등 라이트는 씬에 하나만 처음부터 두고 intensity만 바꾼다. 숨겨진 그룹 안의 라이트는 렌더 목록에서 빠지므로(= 개수가 바뀐 것과 같음) 캐릭터 그룹 밖에 둔다.
- **누수 측정의 기준값:** 처음 그릴 때만 올라가고 일부러 해제하지 않는 자원(공유 Geometry, 투과 재질 렌더 타깃 등)이 있다. 그래서 '페이지를 연 직후'가 아니라 **한 번 순환하고 모두 제거된 뒤**를 기준으로 잡고, N회 반복 후 같은 값으로 돌아오는지 본다. 반복 중에는 `textures − 비행 수`가 일정해야 한다.
- **발사 위치 보정:** 손에 든 천등의 실제 월드 위치에서 출발해야 튀지 않는다. 보정(바닥 아래·몸속)은 이상한 경우에만 걸리게 하고, 머리를 피하는 것은 위치를 순간 이동시키지 않고 처음 1초 동안 **부드럽게 흘러가게**(drift) 한다. 속도도 0에서 올라오게(가속) 해서 출발 순간 움직임이 끊기지 않는다.
- **확인 질문:** 발사 천등의 위치를 store에 매 프레임 쓰면 무엇이 문제인가? 6번째 천등을 발사하면 어떤 컴포넌트가 언마운트되고 어떤 GPU 자원이 해제되는가? 발사 천등마다 pointLight를 붙이면 무엇이 비싸지는가? 페이지 로드 직후 값을 누수 기준으로 쓰면 왜 틀린가?

## 20. 카메라 추적과 보간: 목표와 실제 시선을 나눈다 — 4단계

- **목표 시선과 실제 시선은 다른 값이다.** 목표(천등을 어디쯤 보고 싶은가)는 매 프레임 바뀌어도 된다. 화면에 쓰는 실제 시선은 그 목표를 **천천히 따라가는 상태**로 따로 둔다. 목표를 lerp로 바로 섞으면 목표가 변하는 속도가 곧 카메라 속도가 되어, 연출이 시작될 때 시선이 '확' 꺾인다 (처음 두 번의 구현에서 생긴 문제).
- **각도로 생각한다:** 카메라 위치는 그대로라, 고개를 드는 것은 '평소 시선에서 위아래(pitch)·좌우(yaw)로 몇 도 돌렸는가'다. 오프셋 각도 2개만 상태로 두고, 평소 시선 방향에 더해 시선점을 다시 만든다 (`CameraRig`의 `applyLookOffset`). 오프셋이 0이면 기존 계산과 완전히 같다.
- **smoothDamp (임계 감쇠 스프링):** 값과 속도를 함께 들고 목표 쪽으로 옮긴다. 속도가 0에서 붙어서(가속) 목표 근처에서 0으로 줄어든다(감속). 목표가 갑자기 바뀌어도 **지금 값·속도에서 이어지므로** 복귀가 순간적으로 꺾이지 않는다 (`lib/game/camera.ts`).
  - smoothTime ≈ 목표에 닿는 시간. 0.5% 안으로 들어오는 데 약 3.6 × smoothTime (복귀 0.28초 → 약 1초).
  - **최대 변화 속도 제한:** 한 프레임 이동량을 `maxSpeed × dt`로 자른다 → 어떤 목표가 와도 5°/초보다 빨리 돌지 않는다.
  - 같은 값을 두 번 부드럽게 하면(목표를 서서히 줄이고 + 스프링) 지연이 더해진다. 복귀가 1.9초로 늘어난 원인이었고, 복귀 목표를 바로 0으로 두어 스프링 하나만 남겼다.
- **실제 위치를 '다시 계산'해서 참조한다:** 발사 천등 궤적은 출발 정보 + 경과 시간의 순수 함수(`getFlyingLanternPosition`)다. FlyingLantern이 그리고, CameraRig가 같은 입력으로 다시 계산한다. Three 객체를 공유하는 ref 등록부가 필요 없고, 마운트 순서와 무관하며 할당이 없다.
- **시선이 내려가지 않게:** 천등은 손 높이(평소 시선점보다 낮음)에서 출발한다. 목표 높이를 max(평소보다 조금 위, 천등보다 조금 아래)로 두고, 천등 방향 ± 17°(세로 반화각 25°보다 작게)로 잘라 천등이 화면 밖으로 나가지 않게 한다 (`getLaunchFocusHeight`, 카메라에서 본 각도로 계산).
- **확인 질문:** 목표 시선을 매 프레임 `lerp(현재, 목표, 0.1)`로 따라가면 최대 속도가 제한되는가? 복귀할 때 목표를 0으로 바로 바꿔도 화면이 튀지 않는 이유는? 카메라가 FlyingLantern의 Object3D를 직접 읽지 않고도 같은 위치를 아는 방법은?

## 21. 한 번 재생하는 동작과 이벤트 기반 전환 (AnimationMixer · Crossfade · LoopOnce) — 캐릭터 애니메이션

- **AnimationMixer와 AnimationAction:** mixer는 캐릭터 하나(루트 객체)에 하나다. `mixer.clipAction(clip)`이 클립마다 action을 만들고, action마다 재생 시간(`time`)·속도(`timeScale`)·가중치(weight)·반복 방식(loop)을 따로 가진다. 여러 action이 동시에 재생되면 mixer가 **가중치 비율로 섞어** 본 자세를 만든다. 실제로 시간이 흐르는 것은 `useFrame`에서 부르는 `mixer.update(delta)` 한 곳뿐이다.
- **Crossfade:** `from.crossFadeTo(to, 초)`는 같은 시간 동안 from의 가중치를 1 → 0, to를 0 → 1로 바꾼다. 두 자세를 잠깐 섞어서 갑자기 튀지 않게 한다. to는 먼저 `reset().play()`로 처음부터 재생해 둔다. 가중치는 mixer 시간으로 줄어들므로 **멈춘(끝난) action도 from이 될 수 있다** (Throw 끝 자세 → Praying).
  - 길이는 두 자세 차이에 맞춘다: Idle ↔ Walk 0.2초, Idle/Walk → Throw 0.25초, Throw → Praying 0.4초(끝 자세가 많이 다름), Praying → Idle 0.5초.
- **LoopOnce + clampWhenFinished:** 기본값(`LoopRepeat`)이면 Throw가 끝나자마자 다시 던진다. `setLoop(LoopOnce, 1)`은 한 번만 재생하고, `clampWhenFinished = true`는 끝난 뒤 **마지막 자세에 멈춘다** (false면 바인드 포즈로 돌아가 한 프레임 튄다).
  - 클립 일부만 쓰기: `reset()` 뒤 `action.time = 0.6`으로 앞의 정지 구간을 건너뛰고, `timeScale = 1.3`으로 빠르게 재생한다. 그래서 '놓는 순간'은 **클립 시간**(3.33초)으로 정하고, 실제 경과 시간은 (3.33 − 0.6) / 1.3 ≈ 2.1초다.
- **이벤트 기반 전환:** LoopOnce action이 끝나면 mixer가 `finished` 이벤트(`event.action`)를 보낸다. 매 프레임 '끝났나?'를 따로 재는 타이머 대신 이 이벤트로 다음 단계(Throw → Praying → Idle)로 넘어간다.
  - 이벤트는 **`mixer.update()` 안에서 동기로** 발생한다 → `useFrame` 안이다. 그래서 store 액션 호출은 CODING_CONVENTIONS §7의 '1회성 이벤트' 규칙을 따른다: 판정은 순수 함수(`getNextLaunchPhase`, `shouldReleaseLantern`), 가드(단계·`hasReleased`)를 호출 **전에** 바꾼다.
  - **리스너는 mixer마다 하나**를 effect에서 달고 같은 정리 함수에서 뗀다. 발사할 때마다 달면 리스너가 쌓여 두 번째 발사부터 다음 단계가 두 번씩 실행된다. 리스너가 최신 콜백을 쓰도록 콜백은 ref로 읽는다.
  - 중복·순서가 틀린 이벤트는 상태 전이 표가 거른다 (§8과 같은 방식): THROW가 아닐 때의 `throwFinished`, 재생 중의 `start`는 무시된다.
- **애니메이션 이벤트와 게임 상태 분리:** `CharacterModel`은 '손을 놓았다', '동작이 끝났다'를 콜백으로 알리기만 하고 천등 상태·모드를 바꾸지 않는다. 실제 분리(`launchLantern`)와 복귀(`finishLaunch`)는 store가 전이 규칙으로 다시 확인한다 → 콜백이 두 번 와도 천등은 하나다. 카메라는 store의 `flying` 변화를 보므로 애니메이션을 몰라도 **실제 분리 순간**부터 연출을 시작한다.
- **'같다'가 아니라 '지났다'로 판정한다:** 프레임 간격이 일정하지 않아 클립 시간이 정확히 3.33초인 프레임은 거의 없다. `time >= 3.33`으로 판정하고, 큰 delta로 놓는 시점과 클립 끝을 한 번에 지나면 `finished`에서 한 번 더 놓는다(가드가 있어 두 번 놓이지 않음).
- **루트 모션 정리 (§13 이어서):** Throw는 앞으로 한 발 디디며 루트가 23.7cm 이동한다. 위치는 코드가 정하므로 에셋 변환 단계에서 루트 XZ를 첫 프레임 값으로 고정했다 (높이 Y는 웅크림 표현이라 유지). 대신 디디는 발은 제자리에서 앞뒤로 움직인다.
- **확인 질문:** Throw를 LoopOnce로 바꾸지 않으면 무슨 일이 생기는가? `clampWhenFinished`가 false면 Throw → Praying 사이에 무엇이 보이는가? 발사할 때마다 `mixer.addEventListener`를 부르면 세 번째 발사에서 어떤 증상이 나타나는가? 카메라 연출이 홀드 완료가 아니라 분리 순간에 시작되는 이유는?

## 22. 브라우저 오디오 (Web Audio API · 자동 재생 정책 · 볼륨 · 게임 이벤트 연결) — 플레이 방법·사운드

- **두 가지 재생 방법:**
  - `<audio>`(HTMLAudioElement): 파일을 **스트리밍**한다. 긴 음악(BGM 141초)에 맞다. 디코딩해 메모리에 올리면 약 50MB(141초 × 44.1kHz × 2채널 × 4바이트)라 BGM은 이쪽을 쓴다.
  - `AudioBuffer` + `AudioBufferSourceNode`(Web Audio): 파일 전체를 PCM으로 **디코딩**해 두고 재생한다. 지연이 거의 없고, 같은 소리를 겹쳐 재생하거나 구간(`start(when, offset)`, `loopStart`/`loopEnd`)을 고를 수 있다. 짧은 효과음·발소리·모닥불 반복에 쓴다. 소스 노드는 **한 번만 start**할 수 있어 재생마다 새로 만든다 (가볍다. 버퍼는 공유).
- **오디오 그래프:** Web Audio는 노드를 선으로 잇는 구조다. 소스 → `GainNode`(음량) → … → `destination`(스피커). 채널마다 gain 노드를 하나 두면 BGM·효과음 볼륨이 서로 독립이 된다. `<audio>`도 `createMediaElementSource`로 그래프에 넣을 수 있다 (단 요소 하나당 **한 번만** 연결 가능 → AudioContext를 다시 만들면 `<audio>`도 새로 만든다).
- **자동 재생 정책:** 브라우저는 사용자가 페이지와 상호작용하기 전(클릭·키 입력 = user activation)에는 소리를 내지 못하게 한다. 입력 전에 만든 `AudioContext`는 `suspended` 상태로 시작하고 콘솔 경고가 남으며, `audio.play()`는 `NotAllowedError`로 거부되는 Promise를 돌려준다.
  - 그래서 **첫 `pointerdown`·`keydown` 핸들러 안에서** AudioContext를 처음 만들고 `resume()`·`play()`를 부른다. 거부된 Promise는 `.catch`로 처리해 '처리되지 않은 오류'를 남기지 않고, 완전히 켜질 때까지 다음 입력에서 다시 시도한다. ESC는 user activation이 아니다.
  - 리스너는 `capture: true, passive: true`라 이동·상호작용 키를 막거나 바꾸지 않는다. 별도의 '소리 켜기' 버튼 없이 처음 움직이거나 클릭하는 순간 켜진다.
  - 디코딩은 입력 전에도 된다: `OfflineAudioContext`는 재생 장치가 아니라 제한 대상이 아니다. `AudioBuffer`는 특정 컨텍스트에 묶이지 않아 나중에 만든 AudioContext에서 그대로 재생된다.
- **볼륨 제어:**
  - 사람의 귀는 크기를 로그로 느낀다. 슬라이더 값을 그대로 gain으로 쓰면 오른쪽 절반은 차이가 거의 없다 → `gain = (값/100)²`.
  - `gain.value = x`로 바로 바꾸면 파형이 끊겨 '틱' 소리가 난다. `setTargetAtTime(목표, 지금, 시간 상수)`는 목표값으로 지수 곡선을 그리며 다가간다 (시간 상수만큼 지나면 약 63%). 슬라이더는 0.03초, 모닥불 근접도는 0.25초, 처음 켤 때 페이드 인은 0.8~1.2초.
  - **음소거 ≠ 볼륨 0:** 음소거는 `muted` 플래그만 켜고 볼륨 값은 그대로 둔다. 그래서 해제하면 이전 볼륨으로 돌아간다. BGM은 음소거해도 멈추지 않고 gain만 0 → 해제하면 처음부터가 아니라 이어서 들린다.
- **localStorage와 SSR:** 서버에는 `window`가 없다. 저장 값을 읽는 store는 `typeof window` 확인과 try/catch(사생활 보호 모드 등)로 감싸고, 이 store를 읽는 UI는 모두 `ssr: false`로 불러오는 GameCanvas 아래에 있다 → 서버 HTML이 없어 Hydration 불일치가 생길 수 없다. 저장 값은 외부 입력이라 `parseAudioSettings`가 형식·범위를 검사하고 기본값으로 채운다.
- **반복 재생의 끊김:** 파일 앞뒤에 무음이 있으면 `loop`가 한 바퀴마다 그만큼 끊긴다. campfire.mp3는 앞 0.35초·뒤 0.56초가 무음이라 `loopStart`/`loopEnd`로 소리 있는 구간만 반복한다. bgm.mp3는 끝 4초가 페이드아웃이라 `<audio loop>`로 처음에 돌아가도 자연스럽다.
- **게임 이벤트와 오디오 연결 (책임 분리):**
  - 게임 로직은 오디오를 모른다. 연결부(`GameAudio`)가 store를 **구독**해서 이전 → 다음 상태를 비교한다(`getGameSoundEvents`, 순수 함수). 버튼·E키 어느 쪽으로 실행해도 같은 소리가 나고, 거부된 전이(상태 변화 없음)에서는 나지 않는다.
  - 점화 = `WRITTEN → LIT`. 발사 = 홀드 완료(`LAUNCHING`)가 아니라 **발사 목록에 새 id가 생긴 순간**(Throw에서 손을 놓아 실제로 분리된 순간). store 전이가 한 번뿐이라 소리도 한 번이다. 1회 효과음에는 cooldown도 있어 같은 이벤트가 겹쳐도 커지지 않는다.
  - 발소리는 키 입력이 아니라 **Walk 클립 시간**으로 맞춘다: 발 본 높이를 측정한 발 디딤 시점(0.33·0.85초)을 이전 → 지금 프레임 사이에 지났는지(`countFootstepContacts`) 본다. 막혀서 제자리면 Walk가 재생되지 않으므로 울리지 않는다. footstep.mp3는 걸음 14개가 불규칙한 간격으로 녹음된 파일이라 걸음 하나씩 잘라(구간 표) 재생하고, 앞 걸음과 같은 소리를 연속으로 쓰지 않는다.
  - 모닥불 근접도는 매 프레임 값이라 React 상태를 쓰지 않는다 (`useFrame`에서 엔진 메서드 호출, 값이 0.005 이상 바뀔 때만).
- **엔진 수명:** 오디오 엔진은 React 컴포넌트가 아니라 모듈 싱글턴이다. 모달을 열고 닫거나 HUD가 리렌더링되어도 BGM이 다시 시작되지 않는다. 연결 컴포넌트가 언마운트되면 `shutdown()`으로 AudioContext를 닫는다(디코딩한 버퍼는 남긴다).
- **확인 질문:** 페이지를 열자마자 `new AudioContext()`를 하면 무엇이 보이는가? 음소거를 '볼륨 0으로 바꾸기'로 구현하면 해제할 때 무엇이 필요해지는가? 발사 소리를 `beginLaunch`에 붙이면 화면과 소리가 얼마나 어긋나는가? 발소리를 keydown마다 재생하면 어떤 경우에 틀리는가 (벽에 막혔을 때, 키를 꾹 누를 때)?
