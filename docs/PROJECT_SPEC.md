## 1. 개요

- 3인칭 캐릭터로 숲속 캠프파이어 공간을 이동하며 **천등 받기 → 손글씨 소원 작성 → 점화 → 3초 홀드 발사**를 진행하는 웹서비스.
- 프론트엔드 포트폴리오 프로젝트. AI와 협업하되 핵심 기술은 직접 이해·검증한다.
- 참고 서비스(온라인 절 '산사')의 디자인·에셋은 복제하지 않는다.

### 최우선 목표

1. 외부 3D 모델 없이 Geometry로 만든 **입체** 천등
2. 직접 쓴 손글씨가 3D 천등 앞면에 **정확히**(반전·잘림·왜곡 없이) 반영
3. 숲속 공간을 걸어 다니는 3인칭 캐릭터 (테이블에서 받고 쓰고, 모닥불에서 점화, 어디서든 발사)
4. 소원 작성 시 1인칭 카메라 전환
5. 천등 상태에 따른 일관된 인터랙션
6. 작은 MVP부터 단계별 검증 (한 번에 전부 구현하지 않음)

### 범위 밖 (MVP 전체 기간)

물리 엔진, DB/Supabase, 인증, 멀티플레이, 서버 저장, 커스텀 셰이더, 애니메이션 라이브러리, 자유 시점 회전, 필압·먹 번짐, **모바일 게임 플레이**.

- **[결정] 외부 3D 에셋은 캐릭터(§4)와 숲 배경(§3)에만 사용한다** (2026-11-03 변경, 기존: 캐릭터만). **천등은 계속 Geometry로 직접 만든다.** 원본 GLB 파일은 수정하지 않는다 (메시 삭제·재질 편집 금지).
- Three.js에 내장된 `AnimationMixer`는 '애니메이션 라이브러리'로 보지 않는다 (추가 패키지가 아님).

- **[결정] 버전 호환성 (2026-11-03 재확인):**
  - `@react-three/fiber`의 최신 안정판은 9.8.2이고, peer 범위는 `react`·`react-dom` `>=19 <19.4`, `three >=0.156`이다. 10.x는 canary뿐이라 사용하지 않는다.
  - 설치된 React는 19.3.0, npm 최신은 19.3.1이다. 둘 다 peer 범위 안이다.
  - **React·React DOM을 19.4 이상으로 올리면 R3F peer 범위를 벗어난다.** R3F 안정판이 지원 범위를 넓히기 전까지 올리지 않는다.
- **[결정] 자동 업데이트 방지 규칙:**
  - `react`, `react-dom`, `next`는 이미 `package.json`에 캐럿(^) 없이 정확한 버전으로 적혀 있다. 이 상태를 유지한다.
  - 3D 관련 패키지는 `--save-exact`로 설치해 정확한 버전으로 고정한다 (`three@0.187.0`, `@types/three@0.187.0`, `@react-three/fiber@9.8.2`).
  - 버전 이름 없이 `npm install react`처럼 설치하거나 `npm update`를 실행하지 않는다.
  - peer 충돌이 나도 `--force`나 `--legacy-peer-deps`로 우회하지 않는다. 원인을 확인하고 사용자에게 보고한다.
  - 설치 후 `npm ls react react-dom @react-three/fiber three`로 버전과 invalid·peer 경고를 확인한다. `package-lock.json`도 함께 커밋한다.
- **[결정] 1단계 설치 결과 (2026-11-03):**
  - vitest 5.1.0의 optional peer `@types/node ^22 || >=24`가 기존 `^20`과 충돌했다 (ERESOLVE). 그래서 실행 환경(Node v24)에 맞춰 `@types/node`를 24.19.2로 올렸다.
  - vite가 vitest의 peer로만 설치되면 npm 버그로 rolldown 네이티브 바이너리가 lock에서 빠진다. 그래서 `vite@8.3.5`를 devDependency에 명시했다.
- **[결정] 3D 모델 로딩:** `@react-three/drei`를 설치하지 않으므로, R3F의 `useLoader`와 three에 포함된 `GLTFLoader`(`three/examples/jsm`)로 직접 불러온다. 캐릭터와 숲 배경 모두 같은 방식이다. 추가 패키지는 필요 없다 (두 GLB 모두 Draco·meshopt 압축이 없어 디코더가 필요 없다).
- **[결정] `@react-three/drei`는 설치하지 않는다.** 필요한 기능(카메라, 텍스처)은 R3F + three로 직접 구현할 수 있고, 핵심 개념을 직접 이해한다는 목표와도 맞다. 필요성이 생기면 그때 다시 판단한다.
- **[결정] Zustand는 3단계에서 설치한다.** 1단계 테스트 화면에는 공유 게임 상태가 없다.
- **[결정] Vitest는 순수 함수 테스트 용도로만 사용한다** (node 환경, jsdom·React Testing Library 없음). 상태 전이와 충돌 계산 검증에 필요하다.
- `next.config.ts`에 `cacheComponents: true`가 켜져 있다. WebGL Canvas는 서버에서 렌더링할 수 없으므로 **3D 영역은 Client Component 안에서 `next/dynamic(..., { ssr: false })`로 불러온다.** (`ssr: false`는 Server Component에서 사용할 수 없음 — Next 문서 `02-guides/lazy-loading.md`)

### 좌표계

- Y축 = 높이, XZ 평면 = 이동 공간.
- **[결정] 배경 GLB는 Y축으로 π 회전해 원점에 배치한다.** GLB 원본 좌표 (x, z)는 월드에서 (-x, -z)다. `WorldConfig`의 값은 모두 회전 후의 **월드 좌표**다.
  - 이유: 카메라는 +z 쪽에서 -z를 바라본다 (§4). 원본 그대로면 큰 바위(높이 6.3)와 울창한 숲이 카메라 쪽(+z)에 있어서 캐릭터를 가린다. 회전하면 이것들이 화면 안쪽 배경이 된다. 오프라인 측정에서 캐릭터가 가려지는 위치가 1129칸 중 477칸 → 308칸으로 줄었다 (DEV_LOG).
- 바닥(`Cube_0`, 재질 `Ground`)은 x, z ∈ [-9.7, 9.7]의 정사각형 섬 윗면이고, 높이는 0.60~0.83으로 완만하다. 섬 아래는 흙 절벽(y -14.6까지)이 있는 떠 있는 디오라마 형태다.

### [결정] 이동 가능 영역

플레이어는 아래 조건을 **모두** 만족하는 곳에만 설 수 있다.

1. **바닥 메시 위:** 배경 GLB의 바닥 메시(`Cube_0`)에 위에서 광선을 쏴서 0.5 간격 높이 격자(heightfield)를 만든다. 충돌 원의 중심과 상하좌우 네 점이 모두 바닥 위여야 한다. 바닥이 없는 곳(섬 밖 허공)은 갈 수 없다.
   - 나무·바위·테이블·모닥불 등 다른 메시는 바닥으로 취급하지 않는다. 그 위에 올라갈 수 없다.
   - 캐릭터의 높이(y)는 격자를 쌍선형 보간한 바닥 높이를 따른다.
2. **단차·경사:** 한 번 이동할 때 높이 차가 0.3을 넘거나 경사(높이 차 / 거리)가 0.9(약 42°)를 넘으면 막는다. 오르막·내리막 모두 같다. 현재 바닥의 최대 경사는 약 0.1이라 실제로 막히는 곳은 없지만, 에셋이 바뀌어도 규칙이 유지되게 둔다.
3. **이동 범위 안 (설계값):** 바닥 전체 중에서 카메라를 크게 가리는 구역(울창한 숲 x < -5, 바위 지대 z < -4.5)과 가장자리 0.7을 뺀 빈터다. 충돌 원 전체가 범위 안이어야 한다.
4. **장애물과 겹치지 않음:** 아래 충돌 규칙.

- 물리 엔진은 쓰지 않는다. 바닥이 거의 평평하고 장애물이 정적이라 높이 격자 + 2D 충돌로 충분하다.

### 충돌

- XZ 평면 2D 충돌. 플레이어는 원(반지름 0.4)으로 근사하고, 장애물은 **원 또는 축 정렬 사각형(AABB)** 으로 처리한다.
- 장애물 크기는 각 메시를 몸통 높이(지면 + 0.25~1.8)에서 수평으로 잘라 얻은 단면을 감싸서 정한다. 비스듬한 나무줄기도 단면 기준이라 실제 위치와 맞다.
  - 충돌 대상: 나무줄기, 바위, 테이블(뿌리·받침 나무 포함 사각형 하나), 모닥불(돌 링 전체를 원 하나 + 바깥으로 튀어나온 돌 3개), 등불 기둥, 큰 버섯.
  - **[결정] 머리 높이 장애물은 머리 여유를 더한다 (2026-11-03):** Chibi 머리의 수평 반지름은 최대 0.70으로 충돌 원(0.4)보다 0.30 크다. 충돌 원은 그대로 두고, 상판이 머리 높이(지면 위 0.6~1.38)인 **테이블만** 머리 높이 단면에서 0.30 + 여유 0.02 바깥으로 넓혔다. 나무줄기·바위는 몸통 높이 단면이 이미 머리 위치를 덮어 겹침이 보고되지 않았다.
  - **통과 가능:** 꽃, 풀, 작은 버섯, 흙더미, 조약돌 (장식).
  - 이동 범위 밖의 나무·바위는 닿을 수 없으므로 넣지 않는다.
- **[결정] X축과 Z축을 따로 이동·검사해서 장애물을 따라 미끄러지듯 이동할 수 있게 한다.** 한쪽 축만 누른 채 장애물의 모서리·곡면에 정면으로 부딪히면 멈춘다 (다른 축 키를 함께 눌러야 돈다). 2단계 브라우저 확인에서 거슬리면 법선 방향 밀어내기로 바꾸는 것을 검토한다.
- **[결정] 프레임 delta 상한 0.1초.** 탭이 비활성화됐다 돌아오면 delta가 매우 커지므로, 상한이 없으면 장애물을 뚫고 지나갈 수 있다. 한 번 이동량(3.5 × 0.1 = 0.35)이 가장 얇은 장애물 지름 + 플레이어 지름보다 작다.

### [결정] 지형 경계 숨김

카메라에 섬 가장자리(절벽·허공)가 보이지 않게 한다. 복잡한 구현 없이 아래 세 가지만 쓴다.

1. **바닥 연장 평면:** 섬 바닥 최저점(0.60)보다 조금 낮은 y=0.57에 400 × 400 평면을 깐다. 섬 옆면과 아래 절벽이 가려진다.
2. **가장자리 띠:** 섬 바깥만 덮는 띠 4개를 가장자리 최고점(0.76)보다 높은 y=0.77에 둔다. 연장 평면만으로는 섬 옆면(어두운 수직면)이 얇은 선으로 보이기 때문이다.
3. **안개 + 하늘 배경막:** 안개 색 = 배경색 = 배경막 아래쪽 색. 연장 평면의 먼 끝이 하늘과 이어진다.
   - **[결정 forest-atmosphere] 하늘은 원점 중심 원통 배경막(반지름 80)의 정점 색 그라데이션이다.** 3인칭 카메라는 약 26° 내려다봐서 화면 맨 위가 지평선 아래 1.2°다. 진짜 하늘(배경색·하늘 돔)은 화면에 전혀 들어오지 않는다 (배경색을 마젠타로 바꿔 확인). 원통은 안개 끝(46)보다 멀리 있어서, 완전히 안개에 덮인 바닥 바로 위에 노을 띠가 보인다. `MeshBasicMaterial`(정점 색, 안개·톤 매핑 없음) 하나이고 셰이더·텍스처는 쓰지 않는다.

- 연장 평면과 띠는 **배경 GLB의 `Ground` 재질 객체를 그대로** 쓴다. 색·조명이 섬 바닥과 같고, 재질을 복사하거나 바꾸지 않는다.
- 남는 한계: 화면 옆쪽 가장자리에 아주 가는 선이 보일 수 있다 (2단계 브라우저 확인 항목).

### [결정] 카메라 가림

- 카메라 높이를 지면 + 4.2로 두어 **나무 캐노피 최저점(약 5.7)보다 낮게** 유지한다. 더 높으면 카메라가 잎 메시 안으로 들어가 화면이 덮인다.

  - **실제 시선은 목표로 바로 가지 않는다.** 평소 시선에서의 위아래·좌우 각도 오프셋을 `smoothDamp`(임계 감쇠 스프링 + 최대 각속도 제한)로 옮긴다. 추적 중 최대 5°/초(smoothTime 0.8), 추적 목표도 1.5초에 걸쳐 0 → 1로 커진다 → 고개를 천천히 드는 느낌. 복귀가 시작되면 목표를 바로 0으로 두고 스프링(0.28초, 최대 24°/초)이 지금 시선에서 감속하며 약 1초에 돌아온다.
  - 오프셋이 거의 0(약 0.006°)이 되면 정확히 0으로 두어 기존 계산으로 완전히 돌아간다.
  - 변경 이력: 12° 고정 각도 올리기 → 천등 2초 추적 → (최종) 대기·속도 제한 추적. 앞의 두 방식은 시선이 너무 빨리 올랐다 내려와 부자연스러워 교체했다 (DEV_LOG).
  - 별도 카메라를 만들지 않고, 발사 천등의 궤적도 바꾸지 않는다. 이동·충돌은 그대로 동작하고, 연출 중 이동하면 카메라도 평소처럼 따라간다.
  - 연출 중 새로 발사되면 세기를 이어 가며 새 천등을 따라간다 (`getLaunchLookRestartSec`, 초점 감쇠). 시선 자체는 스프링이 지금 각도·속도에서 이어 가므로 튀지 않는다. 실제 UI로는 한 번 순환에 약 7초가 걸려 5초 연출과 겹치기 어렵다.

### 소원 작성 모드 (WRITING)

- **[결정 3단계] 작성 시점·종이:** 카메라 (-2.81, 3.89, 1.42) → 시선 (-3.3, 2.05, 1.42), 전환 0.6초 (`WRITING_VIEW`, 가림 광선 측정은 DEV_LOG). 종이는 상판 위 y 2.1, 0.7 × 1.05 (2:3).

## 5. 3D 천등

### 형태

- 외부 모델·GLB·Blender를 사용하지 않는다. Geometry + Material로만 만든다.
- 크기: 가로 1.2, 세로 1.8, 깊이 1.2. **앞면 1.2 × 1.8 = 2:3 = Canvas 512 × 768.**
  - **[결정] 깊이를 가로와 같게 둔다 (2026-11-03, 기존 0.7).** 네 옆면이 모두 1.2 × 1.8이 되어 위에서 보면 정사각형 단면이다.
- 구성:
  - 앞면: `PlaneGeometry(1.2, 1.8)` + 손글씨 텍스처
  - 뒷면: 기본 색상 평면
  - 좌우면: 종이 재질 평면 (1.2 × 1.8)
  - **[결정] 상단 어깨 (2026-11-03):** 몸통 위에 높이 0.28의 사각뿔대. 아래는 몸통 윗변과 같고 위는 가로·깊이 모두 0.75배로 좁아진다 (1.2 → 0.9). 몸통과 같은 종이 재질, 글씨 없음. 대만 스펀 천등처럼 어깨가 안쪽으로 꺾이는 실루엣이다.
  - 테두리: 얇은 Box
  - 하단: 불꽃 + 발광 요소
- 모든 요소를 `LanternModel` 하나로 묶고, **수령·소지·점화·발사·작성 미리보기 모두 같은 컴포넌트를 재사용한다.**
- 앞면은 평평하게 유지한다 (곡면·사다리꼴 금지). 둥근 장식은 핵심 기능 검증 후 추가한다.
- **[결정] 각 면은 `side = FrontSide`로 바깥쪽을 향하게 둔다.** DoubleSide를 쓰면 뒤에서 볼 때 손글씨가 좌우 반전된 채로 비친다.

### 색상

- 빨강·주황·노랑·분홍 4종. **`constants/lanternColors.ts` 단일 상수**에 id·이름·HEX를 정의한다.
- 같은 HEX를 2D Canvas 배경, 3D 종이, 색상 선택 UI에서 공유한다.
- **[결정] 2D와 3D의 색 일치:** 텍스처의 `colorSpace = SRGBColorSpace`로 설정한다. 그래도 R3F 기본 톤 매핑 때문에 색이 달라 보이면 종이 재질에 `toneMapped = false`를 적용한다 (1단계 검증 항목).

### 소원 작성 Canvas

- 논리 크기 **512 × 768 고정**. 화면 표시 크기만 CSS로 반응형으로 조절한다.
- 입력 좌표 변환: `(clientX - rect.left) × 512 / rect.width`.
- **[결정] Canvas 내부 해상도는 DPR과 상관없이 512 × 768로 고정한다.** 고해상도 화면에서 조금 흐릴 수 있지만, 텍스처와 1:1로 대응해서 변환이 단순해진다.
- Pointer Events 사용. `setPointerCapture`, `pointerup`, `pointercancel`을 처리한다.
- `touch-action: none`으로 필기 중 스크롤을 막는다.
- 검정 붓: `lineCap = 'round'`, `lineJoin = 'round'`, 고정 두께.
- 기능: 되돌리기, 전체 지우기, 완료(1획 이상일 때만), 취소.
- **[결정] 동시에 여러 손가락으로 입력하면 첫 번째 pointerId만 처리한다.**

### [결정] 손글씨 데이터의 단일 원본 = 획(stroke) 배열

- `strokes: Point[][]` (512 × 768 논리 좌표)를 천등 데이터에 저장한다.
- 텍스처는 `drawLanternFace(ctx, colorHex, strokes)` **결정적 그리기 유틸리티 하나**로 만든다. 이 함수는 전달받은 Canvas 컨텍스트를 변경하므로 순수 함수가 아니다. 다만 같은 입력에는 항상 같은 그림을 그린다. 작성 Canvas 화면과 3D 텍스처가 같은 함수를 쓰므로 결과가 항상 같다.
- **[결정] 순수 함수로 분리하는 대상** (`lib/writing/`, `lib/game/`, Vitest로 테스트):
  - 좌표 계산: `toLogicalPoint(clientX, clientY, rect)` → 512 × 768 논리 좌표 (범위 밖 값은 clamp)
  - 획 데이터 변경: `startStroke`, `appendPoint`, `undoStroke`, `clearStrokes`, `hasInk`. 원본 배열을 수정하지 않고 새 배열을 반환한다.
  - 상태 전이 (§7), 충돌·거리·상호작용 가능 여부 (§3, §8)
- `drawLanternFace`는 단위 테스트 대상이 아니다. 1단계 브라우저 시각 검증으로 확인한다 (node 환경에는 Canvas가 없고, 그리기 결과는 눈으로 확인하는 편이 정확하다).
- 이미지(dataURL·Canvas 요소)를 저장하지 않고 획 배열을 저장하는 이유:
  - 되돌리기와 재편집이 쉽다.
  - 직렬화할 수 있어 상태 저장에 적합하다.
  - 단위 테스트가 가능하다.
  - 원본 데이터가 하나로 유지된다.
- 작성 중인 초안 획은 `WritingOverlay`의 로컬 상태로 관리하고, **완료할 때만 store에 반영한다.** 그래서 취소하면 마지막으로 완료한 내용이 그대로 남는다.

### 텍스처 적용

1. 오프스크린 Canvas(512 × 768)에 색상 배경과 획을 그린다.
2. `new CanvasTexture(canvas)`로 텍스처를 만든다. `colorSpace = SRGBColorSpace`를 설정하고 `flipY`는 기본값(true)을 유지한다.
3. 앞면 Plane의 `map`에 적용한다. 메시 자식이므로 이동·회전해도 표면에 붙어 있다.
4. 다시 작성하면 같은 Canvas에 다시 그리고 `needsUpdate = true`로 갱신한다 (텍스처를 새로 만들지 않음).

- 검증 항목: 상하 반전, 좌우 반전, 잘림, 비율 왜곡 (모서리 마커가 있는 테스트 글씨로 확인).

### [결정] 텍스처 소유권과 생명주기

**원칙: 획 데이터는 공유하고, GPU 텍스처는 공유하지 않는다.**

| 자원                                | 소유자                                                        | 생성                                      | 해제                                             |
| ----------------------------------- | ------------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| 획 데이터 `strokes`                 | store (`held`, `flying[i]`)                                   | 작성 완료 시                              | 발사 천등 제거 시 store에서 삭제                 |
| 오프스크린 Canvas + `CanvasTexture` | **`useLanternTexture`를 호출한 컴포넌트 인스턴스 하나**       | 해당 인스턴스의 `useLayoutEffect` 실행 시 | **같은 effect의 정리 함수**에서 `dispose()`      |
| 천등 Geometry                       | `lib/lantern/lanternGeometry.ts` 모듈 상수 (앱 전체 소유)     | 모듈 로드 시 1회                          | **해제하지 않음.** 개수가 고정이라 누수가 아니다 |
| Material                            | JSX 자식 요소로 선언 (`<meshStandardMaterial />`), R3F가 관리 | 마운트                                    | R3F가 언마운트 시 자동 해제                      |

- `HeldLantern`, `FlyingLantern`, `/lab` 미리보기는 **각자 자기 텍스처를 만들고 각자 해제한다.** 다른 컴포넌트에 텍스처 객체를 넘기거나 store에 저장하지 않는다.
- **발사 시 전환 순서:**
  1. `launchLantern(spawnPos)`가 store 한 번의 갱신으로 `held.status = NONE`으로 바꾸고, `flying`에 `{ id, colorId, strokes(같은 배열 참조), spawn }`을 추가한다.
  2. React 커밋에서 `HeldLantern`이 언마운트되면서 **자기** 텍스처를 해제하고, `FlyingLantern`이 마운트되면서 같은 획 데이터로 **새** 텍스처를 만든다.
  3. 두 텍스처가 서로 독립적이므로, 어느 쪽이 먼저 실행되든 상관없다.
- **공유와 참조 카운트를 쓰지 않는 이유:** React는 커밋할 때 언마운트되는 effect의 정리(cleanup)를 새로 마운트되는 effect의 실행보다 **먼저** 처리한다. 텍스처를 참조 카운트로 공유하면 카운트가 잠깐 0이 되면서, `FlyingLantern`이 받기 전에 텍스처가 해제된다. 이를 막으려면 지연 해제 같은 추가 장치가 필요하다. 512 × 768 텍스처를 한 번 더 그리는 비용은 무시할 수 있으므로 소유자를 하나로 두는 쪽이 단순하고 안전하다.
- **[결정] 텍스처 생성·해제는 하나의 `useLayoutEffect` 안에서 짝을 이룬다** (StrictMode 대응):
  ```
  useLayoutEffect(() => {              // deps: [] — 마운트 1회
    const canvas = 512×768 오프스크린 Canvas
    const tex = new CanvasTexture(canvas)
    textureRef.current = tex
    materialRef.current.map = tex      // 앞면 재질에 명령형으로 연결
    return () => {
      materialRef.current.map = null
      tex.dispose()                    // 이 effect가 만든 것만 해제
      textureRef.current = null
    }
  }, [])
  useLayoutEffect(() => {              // deps: [colorHex, strokes]
    drawLanternFace(ctx, colorHex, strokes); textureRef.current.needsUpdate = true
  }, [colorHex, strokes])
  ```
  - Next App Router는 개발 모드에서 StrictMode가 기본으로 켜져 있다. StrictMode가 적용되는 트리에서는 마운트 → 정리 → 재마운트가 실행된다. (1단계 검증: R3F 9.8.2 Canvas 안에서는 이 이중 실행이 재현되지 않았다. 일반적으로 일어나지 않는다고 보지 않고, 아래 구조를 유지한다. IMPLEMENTATION_PLAN 1단계 완료 조건 참고) 이때 첫 번째 텍스처 T1은 **한 번도 렌더링되지 않은 상태로 해제**되고, 재마운트에서 새 T2를 만든다. **해제된 텍스처를 다시 쓰는 경로가 없다.**
  - 렌더링 중(`useState` 초기화, `useMemo`)에는 텍스처를 만들지 않는다. 렌더링 중에 만든 객체는 effect 정리 함수에서 해제된 뒤에도 같은 값으로 남아 다시 쓰이게 되기 때문이다.
  - `useLayoutEffect`는 브라우저 페인트와 다음 R3F 프레임 전에 실행된다. 그래서 첫 프레임부터 `map`이 연결되어 있고, 글씨가 비어 있는 공백 프레임이 없다.
  - 텍스처를 state에 넣지 않고 ref와 명령형 할당을 사용한다. 이렇게 하면 effect 안에서 setState를 호출하지 않아도 된다 (현재 ESLint 설정의 `react-hooks/set-state-in-effect`가 error 규칙이다).
  - `map`은 JSX prop으로 넘기지 않는다. prop으로 넘기면 R3F가 리렌더링할 때 명령형으로 연결한 값을 덮어쓴다.
- **[결정] 공유 Geometry는 R3F가 해제하지 않도록 넘기는 방식을 고정한다:**
  - R3F는 언마운트할 때 **JSX 요소로 선언되어 R3F가 만든 객체**(`<planeGeometry />`, `<meshStandardMaterial />` 등)를 해제한다.
  - 공유 Geometry는 반드시 `<mesh geometry={LANTERN_GEOMETRY.front}>`처럼 **prop으로만** 넘긴다. JSX 자식 요소, `<primitive attach="geometry">`, `useMemo`로 만든 Geometry는 사용하지 않는다.
  - 천등 그룹에는 `dispose={null}`을 쓰지 않는다. 이 옵션은 하위 Material의 자동 해제까지 막아 Material 누수를 일으킨다.
  - 실제로 해제되지 않는지 1단계에서 검증한다. 개발 모드에서 공유 Geometry에 `addEventListener('dispose', ...)` 경고를 걸어 두고, 마운트·언마운트를 반복해도 경고가 나오지 않는지 확인한다. Three.js는 해제된 Geometry를 자동으로 다시 업로드하므로 화면만 봐서는 문제를 알아챌 수 없다.
- `map`으로 연결한 텍스처는 **R3F가 해제해 줄 것으로 가정하지 않고** 소유자가 직접 해제한다. Material을 해제해도 그 `map`은 해제되지 않는다.

### [결정 forest-atmosphere] 월드 조명 (초저녁)

- 라이트는 **4개로 고정**한다: 반구광(연보라 하늘 / 어두운 보라 바닥), 노을빛 방향광(서쪽 -x·-z 낮은 각도, 약한 분홍), 모닥불 `pointLight`(주황, decay 2, distance 11), 손 천등 `pointLight`(4단계, 아래).
- 모닥불 불꽃은 배경 GLB의 `Mball.018` 메시를 그대로 쓰고, **복제한 Geometry의 정점을 매 프레임 옮겨** 일렁이게 한다 (본·모프·셰이더 없음). 바닥 높이(0.73) 아래 정점은 고정해서 밑동이 장작에서 떨어지지 않는다. 계산은 `lib/game/campfire.ts` 순수 함수.
- 불꽃 `Fire` 재질의 `emissiveIntensity`와 pointLight `intensity`를 같은 흔들림 값으로 함께 바꾼다. 재질은 이 메시만 쓰고, 언마운트 시 원래 값으로 되돌린다.
- 그림자·Bloom(후처리)은 쓰지 않는다. 그림자는 pointLight 하나에 6면 렌더가 더 필요하고, Bloom은 후처리 패스가 더 필요하다. emissive + 톤 매핑으로 먼저 확인한다.

### 조명·발광 (천등)

- 점화 전: 종이 색상만 표시, 발광 없음.
- 점화 후: 하단 불꽃 메시, 종이 재질 `emissive` 강화, 범위가 제한된 따뜻한 `pointLight`.
- **[결정] 소지 중인 천등의 pointLight는 처음부터 마운트해 두고 intensity만 0 ↔ N으로 바꾼다.** Three.js는 라이트 개수가 바뀌면 셰이더를 다시 컴파일해서 화면이 순간적으로 멈춘다.
- **[결정] 발사된 천등에는 pointLight를 붙이지 않고 emissive만 사용한다.** 성능 때문이다.
- 투명 재질과 커스텀 셰이더는 사용하지 않는다.
- **[결정 4단계] 점화 발광 구현:**
  - 종이 5면(앞·뒤·좌·우·어깨)의 `emissive`만 쓴다. 앞면은 `emissiveMap`(손글씨 텍스처) × 안쪽 불빛 색 `LANTERN_INNER_GLOW_HEX`(#ffe2bd), 나머지 면은 `종이색 × 같은 색`이라 다섯 면이 같은 색으로 빛난다. 검정 글씨는 곱해도 검정이라 점화 후에도 읽힌다. 갈색 프레임은 빛나지 않는다.
  - 불빛 색은 4색 모두 채널 크기 순서(색상 계열)가 유지되는 값으로 고른다 (분홍이 살구색이 되지 않게, 테스트).
  - 세기: 손 천등 0.65, 발사 천등 0.8 (`LANTERN_GLOW_CONFIG`). 0.85 이상에서는 톤 매핑 때문에 분홍이 흰 분홍으로 바랬다.
  - 흔들림·점화 연출은 `getLanternGlow`(순수 함수): 모닥불과 같은 `wobble`로 ±8% 흔들리고, 점화 순간 0 → 0.18초 동안 기본의 1.9배까지 밝아졌다가 약 1초 안에 기본 밝기로 돌아온다. 같은 값을 손 천등 pointLight 세기에도 곱한다.
  - 손 천등 pointLight(#ffa252, intensity 2.2, distance 3, decay 2)는 **캐릭터 그룹 밖(씬 루트)**에 두고 매 프레임 손 천등 위치를 따라간다. 캐릭터 그룹 안에 두면 작성 모드에서 그룹이 숨겨질 때 라이트가 렌더 목록에서 빠져 라이트 수가 바뀐다 (셰이더 재컴파일). 범위가 3이라 모닥불 빛(distance 11)과 겹치지 않고 캐릭터 몸·발밑만 비춘다.

### 발사 연출

- 손에서 분리되어 발사 시점의 월드 위치에서 시작한다.
- 상승(Y 증가)하면서 sin 기반으로 좌우로 흔들리고 Y축으로 천천히 회전한다.
- 멀어질수록 작아 보이는 효과는 원근 카메라로 자연스럽게 생기므로 scale을 따로 조절하지 않는다.
- **[결정 4단계] 발사 천등 궤적 (`FLYING_LANTERN_CONFIG`, `lib/game/flight.ts`):**
  - **크기 = 손 천등 크기(0.26)** 그대로다. 발사 순간 갑자기 커지지 않는다.
  - 출발 위치·방향 = 손 천등 그룹의 실제 월드 위치와 Y 회전 (`getLaunchPose`). 바닥 + 0.3보다 낮거나 캐릭터 중심에서 0.4보다 가까우면 보정한다 (평소에는 보정되지 않음).
  - 상승 0.75/초 (1단계 랩 1.6보다 느림), 흔들림 진폭 0.12, 회전 0.35 rad/초. **가속 0.8초:** 위치·속도가 모두 0에서 시작해 출발 순간 튀지 않는다.
  - **머리 피하기:** 손 옆(캐릭터 중심에서 0.37~0.5)에서 그대로 오르면 지면 위 1.0~1.4의 큰 머리(반지름 0.70)를 뚫는다. 그래서 첫 1초 동안 캐릭터 바깥 방향으로 중심 거리 0.95까지 흘러간다 (drift).
  - 1단계 랩은 기본 프로필(`LAB_FLIGHT_PROFILE`, 기존 값·가속 없음)을 그대로 쓴다.
  - 카메라는 발사 천등을 계속 따라가지 않는다. 발사 후 약 5초 동안만 시선이 천등을 따라 봤다가 돌아온다 (§4 발사 연출). 그 뒤 발사 천등은 화면 위로 벗어나고, 20초 뒤 화면 밖에서 제거된다.
- 위치·회전은 `useFrame`에서 `delta` 기반으로 ref에 직접 갱신한다. **프레임마다 React 상태를 바꾸지 않는다.**
- **[결정] 제거 조건:** 높이 > 40 또는 경과 시간 > 20초. **동시에 존재하는 발사 천등은 최대 5개**로 제한하고, 초과하면 가장 오래된 것부터 제거한다.
- 제거되면 `FlyingLantern`이 언마운트되면서 자기 텍스처를 해제한다. 공유 Geometry는 해제되지 않는다 (위 소유권 규칙).
- **누수 검증:** 수령 → 작성 → 점화 → 발사 → 자동 제거를 10회 이상 반복한 뒤 `renderer.info.memory.textures`와 `geometries`가 처음 값으로 돌아와야 한다 (소지 천등 1개 + 남아 있는 발사 천등 수 + PBR용 DFG LUT 텍스처 1개. 이 텍스처는 three가 앱 전체에 하나 만들고 해제하지 않는다).
  - **[결정 4단계] '처음 값'은 1회 순환이 끝나고 발사 천등이 모두 제거된 뒤의 값이다.** 게임 화면에는 처음 그릴 때 한 번만 올라가고 설계상 해제하지 않는 자원이 있다: 공유 천등 Geometry(불꽃·연료 포함), 강조 껍데기, 등불 `Glass`의 투과 렌더 타깃(그 메시가 처음 화면에 들어올 때 생성. 천등 없이 걷기만 해도 textures 3 → 5). 페이지를 막 연 직후 값과 비교하면 이것들이 누수처럼 보인다 (DEV_LOG 4단계).

## 6. 사용자 시나리오

> 2026-11-03 변경: 수령대·책상·야외 이동 단계를 없애고 **테이블(받기·작성) → 모닥불(점화) → 어디서든(발사)** 4단계로 바꿨다.
> 장면 전환은 없고, 천등 상태와 상관없이 이동 가능 영역(§3) 안을 자유롭게 걸어 다닌다.

**[결정] 테이블에서 상태별로 보이는 버튼**

| 상태    | 테이블 범위 안에서 표시                         | E키 실행      |
| ------- | ----------------------------------------------- | ------------- |
| NONE    | '천등 받기'                                     | 천등 받기     |
| BLANK   | '소원 작성하기' + '색상 다시 고르기' (버튼 2개) | 소원 작성하기 |
| WRITTEN | '소원 수정하기'                                 | 소원 수정하기 |
| LIT     | 없음 (상호작용 불가)                            | 없음          |

- 한 대상에 버튼이 2개일 수 있으므로 E키는 **첫 번째(주) 액션**만 실행한다. 보조 액션('색상 다시 고르기')은 클릭으로만 실행한다.

### STEP 1. 천등 받기 (나무 테이블)

- 테이블 범위 안 + 상태 NONE → **'천등 받기'** → 색상 선택 UI (모드 COLOR_SELECT, 이동 잠금).
- 색상 선택 → BLANK. 캐릭터 손에 천등이 렌더링된다.
- **[결정] 색상 선택 UI에는 '닫기'(ESC)가 있다.** 닫으면 상태는 바뀌지 않는다 (NONE이면 NONE, BLANK이면 기존 색 유지).

### STEP 2. 소원 작성 (같은 테이블)

- 테이블 범위 안 + BLANK → **'소원 작성하기'**, **'색상 다시 고르기'**.
- 테이블 범위 안 + WRITTEN → **'소원 수정하기'** (기존 글씨를 불러와 이어서 수정한다). WRITTEN에서는 색상을 바꿀 수 없다.
- 작성할 때만 1인칭 시점으로 바뀐다 (§4 WRITING). 기존 Canvas 손글씨 작성과 CanvasTexture 적용 방식을 그대로 쓴다 (§5).
- 1획 이상일 때만 완료 버튼이 활성화된다. 전부 지우거나 되돌려서 0획이 되면 완료 버튼이 다시 비활성화된다.
- 완료 → WRITTEN, 텍스처 갱신, 3인칭으로 복귀.
- 취소(ESC 포함) → 데이터 변경 없이 복귀.

### STEP 3. 불 붙이기 (모닥불)

- 작성한 천등을 들고 모닥불로 걸어간다.
- 모닥불 범위 안 + WRITTEN → **'불 붙이기'** → LIT. 불꽃과 발광이 활성화된다.
- **[결정] WRITTEN에서만 활성화한다.** NONE·BLANK·LIT에서는 모닥불에 버튼·강조를 모두 표시하지 않는다.
  - **[결정 4단계 변경]** 기존 결정은 BLANK에서 모닥불 앞에 "먼저 소원을 적어 주세요" 안내를 띄우는 것이었다. 4단계 요청에 따라 모닥불 앞 안내는 없앴다. 대신 화면 왼쪽 위 **상태 표시줄이 항상** "빈 천등 · 탁자에서 소원을 적어 주세요"를 보여 줘서, 왜 점화가 안 되는지 알 수 있다. 상태별 문구: WRITTEN "모닥불에서 불을 붙여 주세요", LIT "어디서든 날릴 수 있어요".
- 모닥불 버튼은 불꽃 위(불꽃 최고점 + 0.55)에 뜬다. 강조·거리·방향·히스테리시스·실행 재검증은 테이블과 같은 함수·같은 값이다 (§8).
- LIT 이후에는 다시 작성하거나 색상을 바꿀 수 없다 (테이블 상호작용 없음).

### STEP 4. 천등 날리기 (어디서든)

- **[결정] 버튼 표시 조건:** LIT이면 위치와 상관없이 '천등 날리기' 버튼을 표시한다. 이동 가능 영역 전체가 발사 가능 영역이다 (모닥불·테이블 범위 제한 없음).
- **3초 홀드:** 버튼 pointerdown(주 버튼) 또는 **F** keydown으로 시작하고, pointerup·pointerleave·pointercancel·F keyup·window blur·탭 숨김·모드 변경(작성·색상 선택)·LIT 해제에서 초기화한다.
  - **[결정 4단계 변경] 발사 키는 E가 아니라 F다** (기존: E). 근접 상호작용(E, 대상 위에 뜨는 버튼)과 발사(F, 화면 아래 가운데 고정 버튼)를 키와 위치 모두로 구분한다.
  - 반복 keydown(`e.repeat`)과 이미 누르는 중에 들어온 다른 장치의 시작은 무시한다. 시작한 장치를 떼면 0%로 돌아가므로 짧게 여러 번 눌러 시간을 쌓을 수 없다 (`lib/game/launchHold.ts`).
  - Ctrl·Cmd·Alt와 함께 누른 F(브라우저 찾기 등)는 가로채지 않는다.
  - 버튼은 포인터 캡처를 하지 않는다. 누른 채 버튼 밖으로 나가면(pointerleave) 취소된다.
- **[결정] 진행률은 `performance.now()`로 측정한 경과 시간**으로 계산한다. setTimeout 누적 방식은 쓰지 않는다. 진행 바는 DOM ref로 직접 갱신하고 React 상태로 프레임마다 렌더링하지 않는다.
- **[결정] 홀드 중에 모드가 바뀌면 진행률을 초기화한다.** 홀드 중 이동은 막지 않는다.
- ~~3초가 지나면 `launchLantern()`을 한 번만 호출한다.~~ **[결정 character-animations 변경] 홀드 완료 ≠ 천등 분리.** 실제 흐름:
  1. 3초가 지나면 `beginLaunch()`를 **한 번만** 호출한다 (EXPLORE + LIT에서만 성공). 모드가 `LAUNCHING`이 되고 천등은 **아직 손에 있다**(LIT, 발광 유지). 홀드 버튼은 사라진다.
  2. 캐릭터가 `Throw`를 한 번 재생한다 (앞쪽 정지 구간 0.6초를 건너뛰고 1.3배속). 클립 시간 **3.33초**(손이 머리 위를 지나 몸 앞으로 뻗은 순간, 홀드 완료 약 2.1초 뒤)에 `launchLantern(pose)`로 손 천등의 그 순간 위치에서 분리한다. LAUNCHING + LIT일 때만 성공하므로 두 번 불려도 천등은 하나다.
  3. 발사 카메라 연출(대기 1초 → 추적 3초 → 복귀 1초)은 `flying` 추가를 감지하므로 **실제 분리 순간부터** 시작한다.
  4. `Throw`가 끝나면 `Praying`을 한 번 재생하고, 끝나면 `Idle`로 돌아가며 `finishLaunch()`로 EXPLORE에 복귀한다 (홀드 완료 약 7.4초 뒤). 별도 입력은 필요 없다.
  - LAUNCHING 동안은 탐색 모드가 아니므로 기존 규칙대로 이동·E키·상호작용 버튼·홀드 버튼이 잠기고, ESC(`closeOverlay`)로 풀리지 않는다. 걷는 중에 홀드가 끝나도 그 자리에 멈춰 던진다.
- 발사 후: 소지 상태 NONE, 발사 천등 목록에 추가. 기도가 끝나 탐색으로 돌아오면 다시 테이블에서 새 천등을 받을 수 있다.
- 기존 상승·흔들림·회전 애니메이션과 텍스처 소유권 규칙(§5)은 그대로다.

## 7. 상태 관리

### 천등 상태 (소지 중인 천등)

`NONE → BLANK → WRITTEN → LIT → (발사) → NONE`

| 액션                      | 허용 이전 상태               | 결과                          |
| ------------------------- | ---------------------------- | ----------------------------- |
| `receiveLantern(color)`   | NONE, BLANK                  | BLANK (BLANK이면 색상만 교체) |
| `finishWriting(strokes)`  | BLANK, WRITTEN (strokes ≥ 1) | WRITTEN                       |
| `lightLantern()`          | WRITTEN                      | LIT                           |
| `launchLantern(pose)`     | LIT (모드 LAUNCHING)         | NONE + 발사 천등 추가         |
| `removeFlyingLantern(id)` | —                            | 목록에서 제거                 |

- 위 표에 없는 전이는 모두 **거부**한다 (상태 변화 없음, false 반환). 예: NONE→WRITTEN, BLANK→LIT, LIT→BLANK, LIT에서 다시 작성.
- 전이 규칙은 `lib/game/lanternTransitions.ts`의 **순수 함수**로 두고 Vitest로 테스트한다. store 액션은 이 함수를 호출만 한다.

### 모드 (카메라·UI)

`EXPLORE | COLOR_SELECT | WRITING | LAUNCHING`

- 천등 상태와는 별도 필드로 관리한다.
- **[결정 character-animations] `LAUNCHING`** = 3초 홀드 완료(`beginLaunch`, EXPLORE + LIT) ~ Praying 종료(`finishLaunch`). 카메라는 3인칭 그대로이고, 이동·상호작용은 EXPLORE가 아니므로 잠긴다. `closeOverlay`는 COLOR_SELECT·WRITING만 닫는다.
- `openColorSelect()`, `openWriting()`, `closeOverlay()`처럼 모드 전환도 액션을 통해서만 한다.
- `openWriting`은 상태가 BLANK·WRITTEN이고 모드가 EXPLORE일 때만 허용한다.
- 이동, E키, 상호작용 버튼은 EXPLORE일 때만 동작한다.

### Store 구조 (Zustand 하나)

```ts
type LanternStatus = "NONE" | "BLANK" | "WRITTEN" | "LIT";
type GameMode = "EXPLORE" | "COLOR_SELECT" | "WRITING";

interface HeldLantern {
  id: string;
  colorId: LanternColorId;
  strokes: Stroke[];
  status: LanternStatus;
}
interface LaunchPose {
  spawn: [number, number, number]; // 손 천등의 실제 월드 위치 (보정 후)
  yaw: number; // 손 천등의 Y 회전
  drift: [number, number]; // 머리를 피해 흘러갈 수평 이동량
}
interface FlyingLanternData extends LaunchPose {
  id: string; // 손에 들던 천등의 id 그대로 (React key)
  colorId: LanternColorId;
  strokes: Stroke[]; // 손에 들던 천등과 같은 배열 참조
}

interface GameState {
  held: HeldLantern; // status NONE이면 다른 필드는 의미 없음
  mode: GameMode;
  flying: FlyingLanternData[]; // 순서 = 발사 순서 (앞이 가장 오래됨)
  nearbyInteractionId: InteractionId | null;
  // actions...
}
```

- **store에 넣는 것:** 이벤트로 바뀌는 값 (천등 상태, 모드, 발사 목록, 토스트).
- **ref·Three 객체로 관리하는 것:** 매 프레임 바뀌는 값 (플레이어 위치·회전, 카메라 위치, 발사 천등 위치, 홀드 진행률).
- **[결정] 예외:** 플레이어 위치는 ref로 관리하지만, 근접 상호작용 대상(`nearbyInteractionId`)은 **값이 바뀔 때만** store에 쓴다. HUD가 프레임마다 다시 렌더링되지 않게 하기 위해서다.
- **[결정 3단계] 3단계 store는 `held`·`mode`·`nearbyInteractionId`만 둔다.** `flying`·`toast`와 `lightLantern`·`launchLantern` 액션은 4단계에서 추가한다 (전이 순수 함수는 4개 액션 모두 구현·테스트됨). `receiveLantern`은 COLOR_SELECT, `finishWriting`은 WRITING 모드에서만 받는다 (UI 우회·중복 실행 차단).
- **[결정 4단계] store에 `flying`과 `lightLantern()`·`launchLantern(pose)`·`removeFlyingLantern(id)`를 추가했다.**
  - `lightLantern`·`launchLantern`은 EXPLORE에서만 받는다 (다른 액션과 같은 UI 우회 차단). → character-animations에서 `launchLantern`은 **LAUNCHING에서만** 받도록 바뀌었다 (§6 STEP 4). 전이는 기존 `applyLanternAction`(light·launch)을 그대로 쓴다.
  - `launchLantern(pose)`: 기존 문서의 `launchLantern(spawnPos)`를 출발 정보 묶음으로 바꿨다. 위치뿐 아니라 방향(회전이 튀지 않게)과 drift가 필요해서다.
  - `launchedAt`은 두지 않았다. 목록 순서가 발사 순서이고 경과 시간은 각 FlyingLantern이 ref로 센다.
  - `toast`는 쓰는 곳이 없어 두지 않았다 (BLANK 안내는 상태 표시줄).
  - 목록 관리(최대 5개, 같은 id 중복 방지, 없는 id 제거 시 변화 없음)는 `flight.ts`의 순수 함수 `appendFlyingLantern`·`removeFlyingLanternById`.
- 같은 정보를 useState로 따로 들고 있지 않는다. 단, 작성 중 초안 획은 확정 전 임시 UI 상태이므로 `WritingOverlay` 로컬 상태로 둔다 (중복이 아님).

## 8. 상호작용 시스템

```ts
interface InteractionDef {
  id: "table" | "campfire";
  shape: Collider; // WorldConfig의 충돌 영역을 그대로 참조 (테이블 사각형, 모닥불 원)
  reach: number; // 플레이어 충돌 원 표면에서 대상 표면까지 허용 거리
  // 테이블 BLANK처럼 버튼이 2개일 수 있다. 첫 번째가 E키로 실행되는 주 액션이다 (§6)
  getActions(state): ({ label: string; run: () => void } | { hint: string })[];
}
```

- **[결정 3단계] 바라보는 방향도 판정한다:** 캐릭터 입력 방향(`targetYaw`)과 '플레이어 → 대상 표면의 가장 가까운 점' 사이 각도가 60° 이내(cos ≥ 0.5)여야 한다. 카메라 방향은 쓰지 않는다. 범위 안이라도 등을 돌리면 버튼·강조가 사라진다.
- **[결정 3단계] 히스테리시스:** 시작 reach 0.7 / 60°, 이미 표시 중인 대상은 0.9 / 75°까지 유지 (`INTERACTION_CONFIG`). 표시와 실행 모두 같은 `currentId`(store `nearbyInteractionId`)로 판정한다.
- **[결정 3단계] 3단계 상호작용 대상은 테이블뿐이다.** 모닥불 대상은 4단계에서 추가한다 (그 전에는 모닥불에 강조·버튼이 없다).
- **[결정 4단계] 모닥불 대상 추가:** `{ id: 'campfire', shape: CAMPFIRE_COLLIDER(이동 충돌과 같은 객체), getActionIds: WRITTEN → ['lightLantern'] }`. 거리·방향·히스테리시스 값은 테이블과 같다 (reach 0.7 / 60°, 유지 0.9 / 75°). 강조는 탁자와 같은 inverted hull 컴포넌트(`InteractionHighlight`, 탁자 전용 `TableHighlight`를 일반화)를 돌 링 18개에 쓴다.
- **[결정 3단계] 탁자 선택 강조:** 상호작용 가능할 때 탁자 메시 `Cube001_0`·`Cube001_1`에만 inverted hull(같은 Geometry를 prop으로 재사용, BackSide 단색, 두께 0.035)을 표시한다. 후처리·셰이더·추가 패키지 없음. 배경 GLB 노드는 바꾸지 않는다.
- **[결정] 거리는 중심점이 아니라 대상의 충돌 영역 표면까지 잰다** (2026-11-03 변경). 테이블은 3.4 길이의 사각형이라 중심 거리로 재면 긴 변 끝에서 범위가 맞지 않는다.
- 범위 안인 대상 중 **표면까지 가장 가까운 하나만** 표시한다.
- **[결정] 범위가 겹칠 수 있다.** 테이블과 모닥불은 에셋 안의 고정 위치라 옮길 수 없고, 두 충돌 영역 사이 통로는 폭 1.35뿐이다. 통로에서는 더 가까운 쪽 하나만 표시한다. `reach` 값과 경계 동작은 3단계에서 테스트와 함께 정한다.
- 버튼 클릭과 E키는 같은 `run()`을 실행한다.
- 범위를 벗어나면 버튼을 숨긴다.
- **[결정] 실행 시점 재검증:** 버튼이 표시됐다는 사실을 믿지 않는다. 클릭이나 E키로 실행할 때 `executeInteraction(id)`가 다음을 **다시** 확인하고, 하나라도 맞지 않으면 아무것도 하지 않는다.
  1. 현재 모드가 EXPLORE인가
  2. 플레이어의 **현재** 위치(ref)에서 대상 표면까지의 XZ 거리가 reach 이하인가
  3. 현재 천등 상태에서 그 액션이 가능한가 (`getActions` 재평가)
  4. 마지막으로 store 액션이 전이 규칙으로 한 번 더 확인한다
- 표시 판정과 실행 판정은 **같은 순수 함수** `resolveInteraction(defs, playerXZ, state)`를 사용한다. 그래서 '보이는데 실행 안 됨'이나 '안 보이는데 실행됨' 같은 불일치가 생기지 않는다.
- 이런 검증이 필요한 이유: 근접 대상은 값이 바뀔 때만 store에 반영되므로 한 프레임 늦을 수 있다. 또 버튼을 누른 순간과 실제 실행 사이에 플레이어가 이동했을 수 있다.
- **[결정] HUD 버튼을 클릭한 뒤 포커스가 남아 Space/Enter로 다시 실행되는 문제를 막는다.** 클릭 후 blur하거나 `onMouseDown preventDefault`로 처리한다.
- '천등 날리기' 홀드 버튼은 근접 상호작용과 별도로 표시한다 (§6 STEP 4). 화면 아래 가운데 고정, 키는 F.

## 10. Git 브랜치 운영 규칙

간소화한 Git Flow를 사용한다.

| 브랜치      | 역할                                   |
| ----------- | -------------------------------------- |
| `main`      | 정식 배포 전용. 1차·2차 배포 때만 반영 |
| `develop`   | 검토를 마친 기능을 통합                |
| `feature/*` | 신규 기능 개발                         |
| `fix/*`     | 버그 수정                              |

1. 신규 작업은 최신 `develop`에서 `feature/*`를 만들어 시작한다.
2. 브랜치명은 목적이 드러나게 짓는다 (예: `feature/lantern-prototype`).
3. 구현 후 타입 검사·린트·테스트·빌드로 검증한다.
4. 검증을 마치면 GitHub PR로 `develop`에 병합한다.
5. `main`에서 직접 개발하거나 커밋하지 않는다.
6. 정식 배포를 결정했을 때만 `develop → main` PR로 병합한다.
7. 배포 후 `main`에 `v1.0.0` 같은 태그를 붙인다. 버전은 실제 변경 범위에 따라 정한다.
8. Claude Code는 작업 시작 전에 현재 브랜치를 확인하고 새 기능의 브랜치명을 제안한다.
9. **커밋·푸시·PR 생성·병합은 사용자의 요청이나 승인 없이 진행하지 않는다.**
